# Conformance cases

These cases are the definition of correct behaviour. Each runtime runs every case with scripted host behaviour and virtual time and must write the expected trace byte for byte. The rules they follow are in [execution.md](../execution.md) and the record format in [trace.md](../trace.md); every expected trace here was derived by hand from those pages. A semantic change is a change to these files, reviewed like any other.

## Layout

```
spec/conformance/
  case.schema.json        the schema of case.json
  regen-ir.sh             regenerates every chart's IR with the compiler
  charts/                 the charts, shared between cases
    shop/                 a copy of examples/shop, frozen for the suite
    nest.road  nest.ir.json  …
  cases/
    checkout-retry/
      case.json           the machine, its input and the script
      trace.jsonl         the expected trace
    …
    resume-order/
      case.json
      trace.jsonl
      created.snapshot.json  a saved snapshot the script names "created"
      …
```

A chart's IR sits next to it, named after it with `.road` replaced by `.ir.json`, and is committed: runtimes read the IR, never the chart. Every IR file is generated by the compiler; run `spec/conformance/regen-ir.sh` after changing a chart or the compiler. The shop charts are a copy so that edits to the documentation's example do not silently change the suite.

The `ir` member of each `started` record is the machine's hash from the IR. `regen-ir.sh` rewrites those members from the regenerated IR (`ROADBOOK_BLESS=1 cargo test -p roadbook-conformance`), and nothing else in the traces, except the hashes of saved snapshots: the `ir` and `snapshot.ir` members of `restored` records, and the `ir` member of the snapshot files that a runtime writes or a migration gives (those named by `snapshot` and `suspend` steps and by `migrate`). A snapshot file named only as what a `restore` restores is left alone: it stands for a snapshot saved by an earlier version of a chart.

## case.json

```jsonc
{
  "description": "Two gateway failures with growing backoff, then a successful charge.",
  "requires": [],                             // features beyond the first version's
  "chart": "charts/shop/checkout.road",       // relative to spec/conformance
  "machine": "Checkout",
  "input": { "order": { /* … */ }, "user": { /* … */ } },
  "stub": [],                                 // machines scripted like tasks
  "fns": { "retryDelay": [{ "args": [1], "returns": 200 }, { "args": [2], "returns": 400 }] },
  "actions": {},
  "script": [
    { "task": "chargeCard", "fail": { "_tag": "GatewayUnavailable" } },
    { "advance": 200 },
    { "task": "chargeCard", "fail": { "_tag": "GatewayUnavailable" } },
    { "advance": 400 },
    { "task": "chargeCard", "done": { "chargeId": "c1", "amountCents": 4200 } }
  ],
  "status": "done"
}
```

Every member is required. Values are in their JSON form ([values](../execution.md#values)).

| Member | Meaning |
| --- | --- |
| `description` | What the case checks. |
| `requires` | The features the case needs beyond the first version's, any of: `messaging` for a case whose chart uses `send`, `emit`, `emits`, `on name.Event`, `invoke … as` or `ref`, or that starts several top-level runs (milestone 5); `parallel` for a case whose chart has a parallel state, and `snapshots` for a case whose script has `snapshot`, `restore` or `suspend` steps (milestone 6). `[]` for none. A runner skips, and does not fail, a case that requires a feature its runtime does not implement yet. |
| `chart` | The entry chart, relative to this directory. |
| `machine` | The machine run as the root run, `r1`, which is started first. |
| `input` | Its arguments, keyed by parameter name. Since no other run exists yet, it has no `ref` argument. |
| `stub` | Machines that are scripted like tasks when invoked. Every other invoked machine runs from the chart as a child run. |
| `fns` | For each function, a list of `{"args": [...], "returns": value}`: the result for those positional arguments. A call whose arguments match no entry (compared as canonical JSON) fails the case. Entries that are never called are allowed. |
| `actions` | For each action, a list of `{"args": {...}, "defect": "message"}`: every call of that action with those arguments (keyed by parameter name, compared as canonical JSON) has the host defect `{"kind": "host", "message": "message"}`. Every other action call does nothing and returns at once. |
| `script` | The steps, in order. |
| `status` | The root run's status after the last step: `running`, `done`, `failed`, `cancelled` or `defect`. (Other top-level runs give theirs in their `start` step.) |

Script steps:

| Step | Does |
| --- | --- |
| `{"advance": ms}` | Advances virtual time by `ms`, firing the timers that fall due on the way, one at a time. |
| `{"event": {"_tag": "Cancel", …}}` | Gives the root run the external event, as host code does. With `"run": "r2"`, gives it to that top-level run instead. |
| `{"task": "chargeCard", "done": value}` | Ends the running scripted invoke of `chargeCard` with success. |
| `{"task": "chargeCard", "fail": {"_tag": …}}` | Ends it with that error, any error type of the chart. One the task does not declare reaches the core as `invoke.fail` all the same, which makes it an `undeclared` defect. |
| `{"task": "chargeCard", "defect": "message"}` | Ends it with the host defect `{"kind": "host", "message": "message"}`. |
| `{"cancel": true}` | Cancels the root run from outside. With `"run": "r2"`, cancels that top-level run instead. |
| `{"start": "Order", "run": "r2", "input": {…}, "status": "done"}` | Starts another top-level run of a machine of the chart, as host code spawns one. `run` is its id: `r2` for the first `start` step, `r3` for the next, and so on. In `input`, the value of a `ref` argument is the id of a top-level run started before this one (running or ended), and the runner passes that run's handle. `status` is the run's status after the last step. |
| `{"together": [step, …]}` | Two or more steps, `event` and `task` steps and at most one `advance`, whose inputs are all queued for one run before it takes the first: the way to make an outcome or an expiry arrive after its state was left. |
| `{"snapshot": "s1"}` | Saves the root run (with `"run": "r2"`, that top-level run) as it is now, and compares the [saved snapshot](../execution.md#the-saved-snapshot) with the file `s1.snapshot.json`. The run carries on; nothing is written to the trace. A run that has ended, with a defect too, gives its final snapshot. |
| `{"restore": "s1", "run": "r3", "status": "done"}` | Restores the saved snapshot in `s1.snapshot.json` as a new top-level run ([restoring](../execution.md#restoring-a-snapshot)) of the machine the snapshot names, from the chart's IR, with the clock, timer, trace sink and host the other runs use. `run` is its id, numbered with the `start` steps. With `"migrate": "s2"`, the host gives a migration that returns the snapshot in `s2.snapshot.json`, which must be a snapshot of the machine being restored, the one `s1` names. `status` is the run's status after the last step. |
| `{"restore": "s1", "refused": "ir"}` | The same, but the restore must be refused with that reason (`invalid`, `machine`, `ir`, `migration`, `ended` or `ref`). No run is started, nothing is written to the trace, and no run id is used. |
| `{"suspend": "s2", "run": "r3"}` | Suspends that top-level run (the root run with no `run`): once it is idle or has ended ([suspending](../execution.md#suspending-and-resume)), compares the saved snapshot suspend gives with `s2.snapshot.json`. A run with a running invoke is idle only after later steps have ended it. |

`task` names a task or a stubbed machine. It refers to the one invoke of that name that is running (started, not cancelled, no outcome given yet) in any run; if several runs have one, `"run": "r1.4"` picks one. No match, or an ambiguous one, fails the case.

**Run ids.** The root run is `r1`, the runs of `start` steps and of `restore` steps that are not refused `r2`, `r3`, … in order, and child runs are named as always ([run ids](../execution.md#the-driver)), so `r2.1` is the child started by invoke 1 of `r2`. A `ref` in a trace is one of these ids ([values](../execution.md#values)). The trace groups each top-level run's tree after the previous one's: `r1`, `r1.1`, `r2`, `r2.1`, `r3`. Cases start at most eight other runs, so ids compare as numbers would.

## How a runner works

A runner gives the driver scripted host code and a virtual clock, then drives it like this:

1. Read `case.json` and the chart's IR. Skip the case if it requires a feature the runtime does not implement. Check the IR's version and that it has the machine.
2. Bind the host: every task, and every machine in `stub`, to a scripted invoke that does nothing until the script ends it; every action to one that raises the host defect `actions` lists for its arguments, if any, and otherwise does nothing and returns at once; every function to the `fns` table. Every other machine runs from the chart.
3. Set the virtual clock to 0, start the root run `r1` with `input`, and wait until the runs are **quiescent**.
4. For each step of `script`, in order: fail the case if the step gives an input to a top-level run that has already ended, or (an `event` or `cancel` step) to one that is suspended or being suspended, or if it is an `event`, `task`, `cancel` or `together` step and every top-level run has ended or been suspended; carry out the step; wait until quiescent; then, for each `suspend` step whose run has become idle or ended, compare the snapshot it gave.
5. Check that every `suspend` step has given its snapshot, that the root run's status is `status`, and that each other top-level run's is the `status` of its `start` or `restore` step (a suspended run's is `running`). A run still running is left as it is: the runner does not cancel it and writes nothing more.
6. Arrange the records [grouped by run](../trace.md#order), write each in canonical form followed by a line feed, and compare the bytes with `trace.jsonl`.

**Quiescent** means that every run's queue is empty, no run is carrying out commands, and every child run that has ended has had its outcome taken by its parent, unless the parent has ended too. Only scripted invokes and timers are then pending, and nothing happens until the runner acts.

**Inputs.** Ending a scripted invoke gives its run the `invoke.done`, `invoke.fail` or `invoke.defect` input for that invoke's id; an event step gives its run (the root run, or `run`) an `event` input; a cancel step a `cancel` request. A `start` step starts the run with the clock, timer and trace sink the others use, after the runs it holds a `ref` to; it gives no input to the runs already started, though its run's start step may send them messages. Messages and emitted events are never scripted: runs produce them, and the driver delivers them.

**Together.** Every item of a `together` step is resolved first, in order, against the invokes running before the step (an invoke resolved by an earlier item of the same step no longer counts as running): an `event` item to its run's `event` input, a `task` item to its invoke's outcome, and an `advance` item to the `after` input of every timer due in its window (below), in the order an `advance` step would fire them, after setting the clock to the window's end. Every input of the step must be for the same run; a step whose inputs are for two runs fails the case (which run steps first would then be up to the host's scheduler). The runner then appends all the inputs, in order, to that run's queue in one operation ([several inputs at once](../execution.md#one-queue-per-run)) and waits until quiescent. A scripted invoke whose outcome was appended this way is never ended otherwise; the driver drops it when the core takes the outcome. All records the step causes carry the clock as the step left it.

**Saved snapshots.** A snapshot file holds one saved snapshot on one line followed by a line feed, and matches [`snapshot.schema.json`](../snapshot.schema.json). One that a runtime writes or a migration gives is in [canonical JSON](../ir.md#canonical-json); one that is only restored stands for a snapshot from elsewhere and may write its numbers in any form (`float-forms`). The runner compares what the driver saves by writing it the same way and comparing the bytes. Due times are virtual: the clock when the driver carried out `timer.start`, plus the delay. A `restore` step reads the file, so a case can restore a snapshot that no step saved; since the two runtimes must save the same bytes, restoring the file is restoring what the other runtime saved. With `migrate`, the runner's migration fails the case unless it is called exactly once, with the snapshot being restored (compared as canonical JSON); it returns the named snapshot. A refused restore fails the case unless the driver refuses it, before writing any record, with the reason given.

**Virtual time.** A timer is due at the virtual time at which the driver carried out its `timer.start`, plus its `delay`. `{"advance": d}` from time `now` repeats: of the running timers in all runs that are due at or before `now + d`, take the one with the earliest due time (ties go to the run that comes first in [run order](../trace.md#order), then to the lower timer id); set the clock to its due time; give its run the `after` input; wait until quiescent. When no timer is left in the window, it sets the clock to `now + d`. A timer started while an `advance` is firing timers is in the same window if it falls due at or before `now + d`, where `now` is the clock when the step began. Otherwise timers fire only during `advance`: a timer with delay 0 started by any other step fires at the next `advance`, even `{"advance": 0}`. Records carry the clock's value when written, so everything a step causes has the same `t`.

**What a runner relies on.** The rules above need these of the driver, which [execution.md](../execution.md#the-driver) requires of every driver:

- It reads the time only from the clock it was given, when it writes a record and when it carries out `timer.start`.
- It starts and cancels timers only through the timer it was given, telling it the run id, the timer id and the delay, and it never completes a timer itself, even one with delay 0. A timer's expiry reaches its run only when the timer fires it, or, for a restored timer already due, when the driver carries out `timer.fire`.
- It can save a top-level run, suspend one, and restore a saved snapshot as a new top-level run that shares the clock, timer and trace sink, with a migration of the runner's.
- It queues every input on one queue per run and takes them one at a time, and it can append a list of inputs to a run's queue in one operation.
- It lets the runner wait until quiescent: every run's queue empty and no run carrying out commands.
- It lets the runner start several top-level runs that share one clock, timer and trace sink, give it a started run's handle as a `ref` argument of another, and give events to and cancel any top-level run.

So the runner's own virtual timer records every timer the driver starts, with its run, id and due time, forgets those the driver cancels, and fires them one at a time as above, waiting for quiescence after each. A Rust runner implements the `Timer` trait so. A TypeScript runner gives the driver its own `Timer` service in the same way; Effect's `TestClock` alone does not meet these rules, because `TestClock.adjust(d)` wakes every sleep in the window without waiting for the runs to settle between them, and it does not promise that `Effect.sleep` with a zero duration waits for the clock to move. A runner may still use `TestClock` as the clock records read, setting it to each due time in turn (`TestClock.setTime`) as its own timer fires.

**A case must not depend on scheduling.** With every input of a step for one run, these rules leave four orders open, and no case depends on them:

- Outcomes from two child runs of one parent that both end while the runs settle after a single step: which child ends first is up to the scheduler.
- Inputs that two runs push onto a third's queue in one step, unless one of them finished pushing before the other started. The messages and emitted events of one sender arrive in order ([order per pair](../execution.md#delivering-messages)), and a child's cancel step is over before its parent's step goes on, so in `cancel-parent-messages` the Logbook takes the Worker's note before Boss's. But nothing orders, say, an Inventory's two replies to two Orders that each forward something to a third run.
- A message to a run that is cancelled in the same step: whether the run took the message before the cancel request is up to the scheduler. (A cancel request goes before what is queued, but the run may already have taken the message.)
- A message to a child in the step after the one that started it, which only a `together` can arrange: whether the child has claimed its invoke context yet, and so whether the message is kept for it or pushed (or, if the child ended in its start step, written `undelivered`), is up to the scheduler.

## The cases

| Case | Checks |
| --- | --- |
| `checkout-charged` | An invoke's `done` leads to a final state whose `output` is the result. |
| `checkout-declined` | `fail CardDeclined` is routed by tag, and a final state's `fail` fails the run. |
| `checkout-retry` | The retry loop: an `after` whose delay comes from a function and reads a variable set by the state's entry, under virtual time; invokes restarted with new ids. |
| `checkout-gave-up` | A guarded block tried in order, falling through to `else` once the guard fails; a bare error as the failure. |
| `place-order-checkout` | `PlaceOrder` running `Checkout` from its chart as child run `r1.4`; an `always` that leaves `Confirming` in the step that entered it, after its entry action; actions with arguments. (`Confirming` has no work; `select-rules` shows that a state left this way does not start its work.) |
| `place-order-checkout-stubbed` | The same with `Checkout` stubbed: `r1`'s records are identical, and there is no child run. |
| `place-order-cancel` | `Cancel` on the compound `Processing` cancels its timer and the child invoke of `Paying`; the child run is cancelled from outside and exits its states. |
| `place-order-timeout` | `Processing`'s `after 30s` fires while the child waits in `Backoff`; the child's own timer is cancelled with it. |
| `place-order-defect` | A host defect in the child's task ends the child with a defect, then the parent, which cancels its other work without exit effects. |
| `fetch-fallbacks` | `on *` for an event the state has no `on` for, `fail *` for an unlisted error, and a dropped event. |
| `wizard-done` | A nested final state completes its compound parent, whose `done` transition and then an `always` run in the same step. |
| `nest-effects` | The order of entry, exit and transition effects across three levels; `set` before `do`; an external self-transition restarting work; a transition into the source's own child; an internal transition; exit effects on cancellation from outside. |
| `gate-guards` | Guards tried innermost state first and in document order, falling back to the parent when no branch holds; `and` and `or` short-circuit: the calls they skip take arguments no other call takes and are missing from the function table, so making them fails the case. |
| `race-stale` | An outcome queued before its state was left is traced as `stale` and ignored. |
| `select-rules` | A guarded `on N` that fails stops `on *` in the same state from being tried, and the parent's `on N` is taken; `on *` for an event the state has no `on` for; a guarded `fail E` with no fallback drops the outcome, and the branch for another error is not tried; an `always` enabled with a `done` is taken first, and a completion is discarded when that `always` leaves and re-enters the state; a state with an invoke and a timer left by `always` in the step that entered it starts neither. |
| `root-level` | `entry`, `exit`, `on` and `after` in the machine body: the root's timer starts with the run and survives transitions below it, its `on` is internal, its `after` exits everything below the root, and its `exit` effects run last, before `done`; an expiry queued in a `together` with the event that leaves its state is `stale`. |
| `cancel-child` | A parent leaving the invoking state cancels a child run waiting in its timer: the child's timer is cancelled and its exit effects run at every level, innermost first. |
| `cancel-root` | The same child cancelled because the root run is cancelled from outside; the root's own exit effects run after it. |
| `cancel-child-defect` | A host defect in a child's exit action while its parent cancels it ends the child with the defect, and the parent with the same defect, in the middle of the step that had already finished it. |
| `defect-cancel-child-defect` | A run ending with a defect cancels its children without records, in region order; the first child's cancel step has a host defect of its own, which the parent ignores: it still cancels the second child, whose exit effects run, and writes its own `defect` record. |
| `defect-final-step` | A host defect in the root's exit action, in the step that reaches a top-level final state, ends the run with a `defect` record in place of `done`. |
| `defect-unassigned-guard` | An optional variable with no initial value starts as `null`; a guard of an invoke's `done` that reads an unassigned variable is an `unassigned` defect inside the core, with no `event` record, and the running timer is cancelled without one. |
| `defect-undeclared` | A stubbed machine failing with an error it does not declare is an `undeclared` defect inside the core. |
| `alias-operators` | Comparison, equality and arithmetic on aliases (of an alias) of `int`, `float`, `duration` and an enum behave as on those types, with the alias-typed operand first; a variable whose type is an alias of an optional type starts as `null`. |
| `run-ids` | Ten child runs: in run order `r1.10` comes after `r1.9`, since segments after the first compare as numbers. |
| `child-messages` | A parent sends Pause and Resume to the child it invokes with `as`, which takes them as messages; the child's Progress reaches the parent's `on upload.Progress` as an emitted event of its invoke; the Progress emitted in the step that ends the child is taken before the child's outcome. |
| `child-no-as` | A child invoked without `as` emits: nothing is delivered to its parent. |
| `child-undelivered` | A send to a child that is not running is `undelivered` with `to` `null` and no `sent`: from an `entry` inside the invoking state in the step that enters it, and after the child's outcome was taken by a transition with no target. An emitted event with no `on` is dropped. |
| `child-stale-emit` | What a child emits from its cancel step is stale for its parent, when the parent re-enters the invoking state (whose new child the event would otherwise match) and when it leaves it; what it sends from its cancel step reaches a peer. |
| `cancel-parent-messages` | A top-level run cancelled from outside: its child's cancel step sends to a peer, which takes it, and emits to the parent, which has ended and does not get it; the parent's own exit sends to the peer, which takes it second. |
| `peer-reply` | A request to a peer through a `ref` parameter, a reply emitted to every holder and matched on its id with a guard, a timeout cancelled by the reply; host code sending to the peer. |
| `peer-two-holders` | One emitted event received by two holders of a `ref`: one drops it (its guard fails), the other takes it; a later one reaches only the holder still running; a send in the transition that ends the sender is delivered. |
| `peer-timeout` | An `after` gives up on a peer that does not answer; the peer's late reply is not delivered to the ended run. |
| `peer-stopped` | A send to a peer that has ended: `sent`, then the driver's `undelivered`. |
| `pair-order` | Two sends from one run to another, in one transition, one through a `ref` parameter and one through a `ref` variable, are taken in order; host code sends to a spawned peer, `r2`; a `ref` in `started` and in an action's arguments is a run id. |
| `parallel-entry-exit` | Entering a parallel state enters its regions in document order, each with everything below it; leaving and cancelling exit them innermost first, the last region first; an `on` of the parallel state reached by every leaf's walk is taken once. |
| `parallel-two-regions` | One event taken in two regions in one microstep: both `transition` records, the exits, each transition's effects in region order, the entries; two regions' `always` transitions taken together while settling; an event taken in one region alone. |
| `parallel-conflict` | Of two regions' transitions that would exit the same state, the earlier region's is taken; a region's transition inside the parallel state wins over the parallel state's own, which the other region's walk found. |
| `parallel-leave` | A transition from one region to a state of the other leaves the parallel state and enters it again with all its regions, restarting the other region's timer; one leaving the parallel state from inside a region cancels the other region's timer. |
| `parallel-done` | A parallel state completes when every region is in a final state, a final region from the start; a region's own `done` is tried before the parallel state's. |
| `parallel-work` | Invokes and timers in two regions and on the parallel state start in document order; work restarts in one region alone; leaving cancels every region's work, the later region's first. |
| `parallel-in-compound` | A parallel state inside a compound state, left by the compound state's transition: both regions, then the parallel state, then the compound state are exited, and the cancelled timer never fires. |
| `snapshot-at-rest` | A run at rest saved and restored as a new run (`restored`), suspended once idle (`suspended`) and restored again to finish; suspending an ended run gives its snapshot; restoring an ended snapshot is refused (`ended`). |
| `snapshot-running-task` | A run saved while its child machine runs: restoring restarts the invoke with its id and fresh arguments, and the child starts again from the beginning as a new child run. |
| `snapshot-timer` | A timer is saved with its deadline: restored before it, it restarts for the time left and expires with the original; restored after it, its expiry is queued at once. |
| `snapshot-migration` | A snapshot with another hash is refused (`ir`); with a migration it is restored, and `restored` names the old hash. |
| `snapshot-refusals` | A migration whose result is a snapshot of another machine is refused (`machine`); a running snapshot with a `result` does not fit (`invalid`); a snapshot that ended with a defect of an unknown kind matches the schema and is refused as `ended`. |
| `snapshot-ended` | Saving a run that has ended gives its final snapshot: `done`, `cancelled` and `defect`. |
| `float-forms` | Integers written as floats (`1.0`, `-0.0`, `10000.0`) in a snapshot and an event are the integers, and are saved in integer form. |
| `resume-order` | The request-handler flow: create and suspend, restore and pay (suspend waits for the task the payment started), restore and deliver, and a late payment to a restored order whose deadline passed, which expires first. |
| `redact-values` | Redaction (`vault.road`, its types in another file): a sensitive parameter, a field of an alias of a record, inside a list of an alias and an optional, in `started`, `action` and `invoke.started` arguments, `event` and `dropped` inputs, an error's field in `invoke.fail`, `set` of a sensitive variable and of a record, a list a function returned, a stale result (redacted as every task's and machine's result would be), and `done`; functions get the real values. |
| `redact-failure` | An error's sensitive field in the variable it is set to and in `failed`. |
| `redact-child` | Redaction in messages to and from a child (`teller.road`): its arguments and `started`, an `undelivered` send before it runs, `sent` and the child's `message` input, its `emitted` event and the parent's `emitted` input, a sensitive variable set from it. |
| `redact-peer` | Redaction between peers: `sent` and `message`, an `emitted` input through a `ref`, and the driver's `undelivered` after `sent` to an ended run, which repeats the redacted value. |
| `redact-snapshot` | A saved snapshot keeps the real values; the `restored` record of the run restored from it shows them redacted. |
